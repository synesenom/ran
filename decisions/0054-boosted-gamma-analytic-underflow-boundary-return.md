# ADR-0054: Rejection samplers with an analytically-provable underflow/overflow boundary return that boundary value instead of throwing

**Date**: 2026-08-11
**Status**: Accepted

## Context

[ADR-0049](0049-continued-fraction-convergence-throw.md) established that an iterative numerical primitive without a bounded-error guarantee — including the generic rejection sampler in `src/algorithms/rejection.js` — throws `Error` when it exhausts its iteration budget, because "a rejection sampler that exhausts its trial budget has produced no sample at all... so silently returning something would have to be a fabricated value."

`src/dist/_gamma.js`'s `boostedGamma(r, a, b)` samples `Gamma(a, b)` for `a < 1` via the boost identity `X · U^(1/a)` (`X ~ Gamma(a+1, b)`, `U ~ Uniform(0,1)`), guarded by a `while (result === 0)` rejection loop (added for #1379) that redraws whenever the boost factor underflows to exact `0.0`. For shape `a` below a precisely derivable threshold `a* ≈ 3.13×10⁻¹³` — derived from the xoshiro128+ PRNG's 32-bit output resolution and `Number.MIN_VALUE`'s underflow boundary: `a* = ln(u_max) / ln(Number.MIN_VALUE)` where `u_max = 1 - 2⁻³²` is the largest value the PRNG can produce below 1 — **every one of the PRNG's `2^32` possible outputs** underflows the boost factor to exactly `0.0`. Below `a*`, the rejection loop has provably zero acceptance probability and never terminates (#1384).

This is a different situation from the continued-fraction and generic-rejection-sampler cases ADR-0049 covers. There, an exhausted budget leaves the last iterate "arbitrarily far from the true value, with no way for the caller to tell" — the loop simply ran out of budget before converging, but more iterations (or a larger budget) would eventually have produced a materially different, better answer. Here, for `a < a*`, no additional iterations would ever change the outcome: the true `Gamma(a, b)` variate is, for every possible draw the PRNG can produce, provably smaller in magnitude than `Number.MIN_VALUE`, the smallest positive value float64 can represent. The correctly-rounded IEEE-754 double-precision representation of that true value genuinely *is* `0.0` — not a truncated partial computation, but the exact answer the type system is capable of expressing. Per [ADR-0015](0015-return-value-and-error-conventions.md)'s fourth channel, "the mathematically correct value happens to be zero" is not an error condition.

The same reasoning applies in the opposite direction to `InverseGamma`, `BetaPrime`, and `StudentT`, which compose `boostedGamma`'s output via reciprocal or ratio transforms (`1/x`, `x/y`) guarded by their own `while (!Number.isFinite(...))` rejection loops (also added for #1379): once the underlying gamma draw is provably `0.0` (or provably below `1/Number.MAX_VALUE` in magnitude), the reciprocal or ratio provably overflows to `Infinity` for every possible draw, and `Number.MAX_VALUE` — the largest representable finite double — is the correctly-saturated boundary representation of that true (unrepresentably large) value.

## Decision

A rejection-sampling loop composed from `_gamma.js`'s boost identity (`boostedGamma` itself, and its downstream reciprocal/ratio consumers in `InverseGamma`, `BetaPrime`, `StudentT`) returns the analytically-provable **boundary value** — `0.0` for underflow, `Number.MAX_VALUE` (sign-adjusted where relevant) for overflow — instead of throwing, when it can be established **analytically, in closed form, ahead of sampling** (not merely inferred from "the loop ran a long time") that every possible draw the PRNG's finite output space can produce leads to that same floating-point-representable boundary. This is narrower than a general license to swallow non-convergence: it applies only where the boundary condition is provable independent of which of the PRNG's `2^32` outputs actually occurs, not where a large-but-finite iteration count merely made success statistically unlikely within an arbitrary budget.

Where the boundary is *not* analytically provable for a given input — i.e. `a >= a*`, where the boost loop has a genuine, if possibly very small, positive acceptance probability — the existing rejection loop keeps sampling per ADR-0049's default (bounded by a generous iteration cap sized against the issue's own measured worst case, not the small generic `MAX_ITER = 100` used by `rejection.js`, since the boost loop's legitimate near-boundary acceptance rate can require far more trials than a general-purpose rejection sampler's `MAX_ITER` budget assumes).

## Consequences

**Easier**: A future distribution composing `_gamma.js` (or any other sampler with a similarly provable, PRNG-resolution-derived underflow/overflow boundary) has a documented, narrow escape hatch for extreme parameter regimes that doesn't require inventing a new ad hoc sentinel value or silently hanging. The distinction from ADR-0049's default is explicit and testable: can the boundary outcome be derived in closed form from the PRNG's known output cardinality, or not?

**Harder**: This is now the second documented exception to ADR-0049's "throw on exhausted budget" default (the first being Chandrupatla's monotone-bracket guarantee). A future contributor extending this pattern to a new sampler must re-derive their own analytic proof that the boundary is unavoidable for *every* representable PRNG output — not assume by analogy that "returning a saturated constant on failure" is generally acceptable. Misapplying this exception to a case where the terminal state is only empirically likely, not analytically forced, would silently reintroduce the fabricated-value problem ADR-0049 was written to prevent.
