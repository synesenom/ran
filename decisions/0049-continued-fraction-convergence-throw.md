# ADR-0049: Iterative primitives without a bounded-error guarantee throw on exhausted convergence budget

**Date**: 2026-08-03
**Status**: Accepted

## Context

`src/special/marcum-q.js`'s `_fc` (#1286) and `src/special/bessel.js`'s `_hi` (#1311) both compute a ratio via a continued fraction, and both throw `Error` when the fraction fails to converge within a regime-aware iteration budget (`_assertFcConverged`/`_assertHiConverged`). This mirrors `src/algorithms/rejection.js`, which throws when rejection sampling exhausts `MAX_ITER` trials without an acceptance.

[ADR-0015](0015-return-value-and-error-conventions.md) established four return-value channels — `throw` for caller/programming errors, `NaN` for a valid query with a mathematically indeterminate answer, `Infinity` for a valid query that diverges, and `0` for a genuinely zero result — but does not name a fifth situation these three files actually hit: an iterative numerical primitive exhausts its iteration budget for an **in-domain input that has a genuine, finite, well-defined answer**. `I_nu(z) / I_{nu-1}(z)` (`_fc`) and the analogous spherical-Bessel ratio (`_hi`) exist and are finite for every valid `(nu, z)` / `(n, x)`; the continued fraction simply failed to reach that value within its budget. That is not "no such value exists" (`NaN`'s definition) and not "the value grows without bound" (`Infinity`'s definition) — it is an algorithmic failure to compute a determinate answer, a case ADR-0015's four channels do not cover.

Complicating the picture, this repository's two general-purpose root-finders — `src/algorithms/chandrupatla.js` and `src/algorithms/newton.js` — do the opposite on the same trigger (exhausted `MAX_ITER`): they silently return the best iterate reached, with no throw and no `NaN`. `chandrupatla.js` throws only for a genuinely invalid bracket (`f(a)` and `f(b)` same sign), which is an ADR-0015 category-1 caller error, not a convergence-budget question. Read naively, this looks like an unprincipled split: some iterative primitives throw on exhausted budget, others don't.

The split is not arbitrary. `_fc` previously behaved like `chandrupatla`/`newton` — it silently returned an unconverged value once `z` exceeded roughly 250–300 — and that was a **bug**, not a preserved design choice: `NoncentralChi2(200, 2000).cdf(2080)` was silently off by `5.1e-08` relative with no signal at all (fixed by #1286; see `solutions/special-functions/2026-08-02-1200-marcum-fc-slow-convergence.md`). The reason a silently-truncated continued fraction is dangerous, while a silently-truncated bisection/Chandrupatla root search is not, is a property of the algorithm, not a stylistic preference: Chandrupatla's bracket shrinks monotonically every iteration by construction, so *whichever* iterate the loop exits on — whether by tolerance or by budget — is guaranteed to lie within a known, shrinking bound of the true root. An unconverged continued fraction carries no equivalent guarantee; its last partial ratio can be arbitrarily far from the true value with no way for the caller to tell. The same reasoning applies to `rejection.js`: a rejection sampler that exhausts its trial budget has produced *no* sample at all (there is no "best partial sample" to fall back to), so silently returning something would have to be a fabricated value.

## Decision

An iterative numerical primitive that exhausts its iteration budget **throws** `Error` if it has no bounded-error guarantee tying its last iterate to the true answer regardless of why the loop exited (continued fractions: `_fc`, `_hi`; rejection sampling: `rejection.js`). A primitive that does carry such a guarantee (monotone-bracket root-finders: `chandrupatla.js`) may continue to silently return its best iterate on exhausted budget, since that iterate remains a meaningfully bounded approximation of the true root either way.

`NaN` is reserved for ADR-0015's original meaning — a valid query whose answer is mathematically indeterminate or does not exist (Cauchy's mean, `0/0`) — and is **not** the right channel for "an iterative algorithm failed to converge for an input that has a genuine finite answer." Returning `NaN` here would misrepresent an algorithmic failure as mathematical non-existence, the same class of misleading silent signal ADR-0015 was written to prevent.

`@throws` JSDoc documents this at the point closest to where each public consumer actually encounters it:
- `besselISpherical(n, x)` and `besselISphericalExpScaled(n, x)` (`src/special/bessel.js`) — the two public exports through which `_hi`'s throw can surface directly.
- `Distribution.prototype.pdf(x)` (`src/dist/_distribution.js`) — a single `@throws` tag naming the actual, narrow scope (currently: `NoncentralChi`/`NoncentralChi2` with odd `k`, reachable only via `besselISphericalExpScaled`), rather than a generic "may throw" note. `hazard()`, `lnPdf()`, `lnL()`, `aic()`, and `bic()` all call `pdf()` directly or transitively and do not need their own repeated copy of the same tag — matching the "document the propagation path... once" alternative and avoiding six near-identical `@throws` blocks that would misleadingly suggest every one of this base class's 80+ distributions can throw from `pdf()`.

## Consequences

**Easier**: Future iterative primitives added to `src/special/` or `src/algorithms/` have a documented rule to follow: throw on exhausted budget unless the algorithm has a genuine bounded-error guarantee like Chandrupatla's monotone bracket. The chandrupatla/newton vs. rejection/`_fc`/`_hi` split is now a stated, justified convention rather than an unexplained inconsistency a future contributor might "fix" in the wrong direction.

**Harder**: `newton.js` still has no documented guarantee comparable to Chandrupatla's monotone bracket — it silently returns its last iterate on exhausted budget with no post-loop check at all. This ADR does not audit or change `newton.js`; a future pass may need to either establish it shares Chandrupatla's bounded-error property or bring it into the throwing camp.
